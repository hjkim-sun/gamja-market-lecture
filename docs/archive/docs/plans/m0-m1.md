# M0 + M1 태스크 분해

> 입력 스펙: [`docs/specs/auth-and-profile.md`](../specs/auth-and-profile.md), [`docs/specs/request-crud-and-listing.md`](../specs/request-crud-and-listing.md)
> 분해 기준: **파일 경계.** 역할(설계/구현/리팩터)로 쪼개지 않는다.
> 태스크 5개, 의존 깊이 3단계.

## 실행 순서

```
T1 (계약 확정)
 ├─► T2 (web 골격 + 인증 화면) ─► T4 (구해요 화면)
 └─► T3 (supabase 스키마 + 프로필 API) ─► T5 (구해요 API)
```

**동시에 돌아가는 조합은 (T2, T3)와 (T4, T5) 둘뿐이며, 두 조합 모두 `web/` ↔ `api/`+`supabase/`로 트리가 완전히 갈린다. 소유 경로 충돌 없음.**

`api/` 트리는 T3 → T5로, `web/` 트리는 T2 → T4로 **순차 인계**된다. 동일 파일(`api/main.py`, `web/app/layout.tsx` 등)을 두 태스크가 만지더라도 시점이 겹치지 않는다.

### 루트 파일에 대하여

두 developer 에이전트의 쓰기 범위는 `web/**`(front)와 `api/**`, `supabase/**`, `docs/contracts/**`(backend)뿐이다. 저장소 루트에는 어떤 파일도 만들지 않는다. **환경변수 템플릿은 `web/.env.example`과 `api/.env.example`로 각 트리 안에 둔다**(PRD §13: 접속 정보는 환경변수로만 참조, 키 하드코딩 금지).

## T1 — API 계약 확정

| 항목 | 내용 |
|---|---|
| **담당** | `backend-developer` |
| **소유 파일** | `docs/contracts/api.md` |
| **선행 태스크** | 없음 |
| **입력** | `docs/specs/auth-and-profile.md`, `docs/specs/request-crud-and-listing.md` |

### 할 일

두 스펙에 나오는 **모든 엔드포인트**의 계약을 코드보다 먼저 문서로 확정한다. M0 엔드포인트만이 아니라 **M1 엔드포인트까지 한 번에** 확정한다 — 그래야 T2와 T4의 프런트가 mock으로 앞서 나갈 수 있다.

포함해야 할 것:

- `GET /me`, `PUT /me`, `POST /requests`, `GET /requests`, `GET /requests/{id}`, `PATCH /requests/{id}`, `DELETE /requests/{id}`, `POST /requests/{id}/close`
- 각 엔드포인트의 요청 본문 / 성공 응답 / **모든 에러 응답**(상태 코드 + `code` 문자열 + 발생 조건)
- 공통 에러 봉투의 최종 형태와 필드명
- 인증 헤더 형식, 토큰 검증 실패 시 응답
- **페이지네이션 방식의 확정** — 스펙은 "한 번에 최대 20건 + 다음 페이지 존재 여부를 응답만으로 판단 가능"만 요구한다. offset 방식인지 cursor 방식인지, 응답 필드명이 무엇인지는 이 태스크에서 정한다.
- 실제로 복사해 쓸 수 있는 **예시 JSON**(성공 1개, 에러 1개 이상). 프런트는 이 JSON을 그대로 mock에 넣는다.

### 완료 조건

전용 테스트가 없는 문서 태스크다. 다음이 모두 참이면 끝이다.

- [ ] 위 8개 엔드포인트가 모두 문서에 있고, 각각 성공 응답과 **최소 하나 이상의 에러 응답**이 적혀 있다.
- [ ] 두 스펙의 수용 조건에 등장하는 모든 `code` 문자열(`unauthorized`, `profile_not_found`, `nickname_taken`, `validation_error`, `forbidden`, `request_not_found`, `request_not_editable`, `request_not_open`, `request_has_offers`, `profile_required`)이 문서에서 검색된다.
- [ ] 목록 응답 예시에 `offer_count` 필드가 있고 값이 `0`이다.
- [ ] 어떤 응답 예시에도 `contact_type` / `contact_value` / 이메일이 등장하지 않는다.
- [ ] 확정 후 `front-developer`에게 계약 확정 사실을 통보했다.

## T2 — web 골격 + 인증/온보딩 화면

| 항목 | 내용 |
|---|---|
| **담당** | `front-developer` |
| **소유 파일** | `web/**` (T4가 가져갈 `web/app/requests/**`, `web/components/request/**`, `web/lib/api/requests.ts` 제외) |
| **선행 태스크** | T1 |
| **입력** | `docs/specs/auth-and-profile.md`, `docs/contracts/api.md` |

### 할 일

- Next.js(App Router + TypeScript) 프로젝트 초기화, vitest + @testing-library/react 설정, `web/.env.example`
- `@supabase/ssr` 기반 세션 관리와 쿠키 갱신 미들웨어
- 가입 / 로그인 / 로그아웃 / 온보딩(닉네임 입력) 화면
- 보호 라우트 가드: 비로그인 → `/login`(원래 목적지 복귀 포함), 프로필 미등록 → `/onboarding`
- 하단 고정 탭 네비게이션 골격(PRD §7.1), 375px 기준 레이아웃
- FastAPI 호출용 클라이언트(인증 헤더 부착, 에러 봉투 파싱)와 홈 화면 껍데기

**백엔드(T3)를 기다리지 말 것.** `GET /me` / `PUT /me`는 계약 문서의 예시 JSON 그대로 mock 해서 진행한다.

### 완료 조건

`auth-and-profile.md`의 **AC1~AC15, AC21~AC25**를 옮긴 프런트 테스트가 전부 green. 특히 다음이 각각 독립된 테스트로 존재해야 한다.

- 잘못된 비밀번호 로그인 시 에러 메시지가 렌더된다 (AC11)
- 닉네임 409 응답 시 "이미 사용 중" 메시지가 렌더된다 (AC8)
- 비로그인 상태로 `/requests/new` 접근 시 `/login`으로 이동한다 (AC14)
- 프로필 없는 로그인 사용자가 홈 접근 시 `/onboarding`으로 이동한다 (AC5)
- `web/` 소스 어디에도 `service_role`이 등장하지 않는다 (AC23)

## T3 — Supabase 스키마 + FastAPI 골격 + 프로필 API

| 항목 | 내용 |
|---|---|
| **담당** | `backend-developer` |
| **소유 파일** | `api/**`, `supabase/**` |
| **선행 태스크** | T1 |
| **입력** | `docs/specs/auth-and-profile.md`, `docs/contracts/api.md` |

### 할 일

- FastAPI 프로젝트 초기화, pytest + httpx.AsyncClient 설정, `api/.env.example`
- Supabase JWT 검증 의존성 — 사용자 식별은 **검증된 토큰의 `sub`** 에서만
- 공통 에러 핸들러(계약의 에러 봉투 형태로 직렬화, 내부 정보 비노출)
- `supabase/migrations/`에 `profiles` 테이블 마이그레이션 + RLS 활성화 + 정책
- `GET /me`, `PUT /me`

### 완료 조건

`auth-and-profile.md`의 **AC7~AC9, AC16~AC22**를 옮긴 pytest가 전부 green. 특히:

- 헤더 없음 / 만료 토큰 / 서명 불일치 각각에 대해 401 `unauthorized` (AC16, AC17)
- 본문에 남의 user_id를 실어도 응답이 바뀌지 않는다 (AC18)
- **닉네임 UNIQUE 경합 테스트** — 사전 조회 if 문이 아니라 DB 제약이 막는 것을 확인 (AC9)
- 성공 응답에 `contact_type` / `contact_value`가 없다 (AC19)
- `profiles`에 RLS가 켜져 있고 정책이 마이그레이션에 함께 들어 있다

## T4 — 구해요 작성 / 목록 / 상세 화면

| 항목 | 내용 |
|---|---|
| **담당** | `front-developer` |
| **소유 파일** | `web/app/requests/**`, `web/components/request/**`, `web/lib/api/requests.ts` (+ 홈 목록 연결을 위한 `web/app/page.tsx`) |
| **선행 태스크** | T2 |
| **입력** | `docs/specs/request-crud-and-listing.md`, `docs/contracts/api.md` |

### 할 일

- 글쓰기 폼(제목·설명·카테고리·가격 범위·지역·마감일), 클라이언트 검증과 서버 400 응답 표시
- 목록 화면: 최신순, 20건 페이지네이션, 상태 배지(텍스트 병기), 제안 수, **로딩 / 빈 상태 / 에러 상태 3종**
- 상세 화면: 전문 표시, 404 화면, 본인 글일 때만 수정/삭제/조기 마감 노출, 삭제 확인 단계

### 완료 조건

`request-crud-and-listing.md`의 **AC1~AC3, AC7, AC8, AC11~AC14, AC16~AC19, AC21~AC24, AC26, AC27, AC29**를 옮긴 프런트 테스트가 전부 green. 특히:

- 목록 0건 → 빈 상태, 요청 실패 → 에러 + 재시도 (빈 상태와 에러 상태가 서로 다른 화면임을 검증) (AC13, AC17)
- 404 응답 시 빈 상세 껍데기가 아니라 "글을 찾을 수 없습니다"가 렌더된다 (AC21)
- 남의 글 상세에 수정/삭제/마감 버튼이 없다 (AC22)
- API mock의 응답 형태가 `docs/contracts/api.md`의 예시 JSON과 일치한다

### 주의

**카테고리는 자유 태그로 확정됐다**(Q4, 2026-08-13). 텍스트 입력 한 칸이면 되고 `select`나 허용 목록이 필요 없다. 자동완성은 M1 범위 밖이다.

## T5 — 구해요 API + 스키마

| 항목 | 내용 |
|---|---|
| **담당** | `backend-developer` |
| **소유 파일** | `supabase/migrations/*_requests.sql`, `api/`의 requests 라우터·스키마·테스트 (+ 라우터 등록을 위한 `api/main.py`) |
| **선행 태스크** | T3 |
| **입력** | `docs/specs/request-crud-and-listing.md`, `docs/contracts/api.md` |

### 할 일

- `requests` 테이블 마이그레이션: `status` 5개 값 전부, **`price_max >= price_min` CHECK 제약**, RLS + 정책
- `POST` / `GET(목록)` / `GET(상세)` / `PATCH` / `DELETE` / `POST /close`
- 만료 파생 계산: `expires_at <= now()`이고 `status='open'`인 글은 응답에서 `expired`, 기본 목록에서 제외
- `offer_count`는 상수 `0`으로 응답에 포함

### 완료 조건

`request-crud-and-listing.md`의 **AC1, AC3~AC6, AC8~AC10, AC11, AC14~AC16, AC20, AC25~AC28**을 옮긴 pytest가 전부 green. 특히:

- `price_min > price_max` 삽입이 **DB CHECK에서** 거부된다 (AC4)
- 남의 글 `PATCH` / `DELETE` → 403 (AC25)
- `closed` 글 `PATCH` → 409 `request_not_editable`, 재마감 → 409 `request_not_open` (AC27, AC28)
- 만료된 글이 기본 목록에서 빠지고 상세에서 `expired`로 보인다 (AC14, AC23)
- 상세 응답에 작성자 이메일·연락 수단이 없다 (AC20)
- 21건 중 20건 + `has_next` 참 (AC15)
