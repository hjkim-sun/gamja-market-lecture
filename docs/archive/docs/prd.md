## 1. 한 줄 정의

**감자마켓은 사는 사람이 먼저 말하는 중고 거래 플랫폼입니다.**
구매자가 "이런 걸 구합니다"를 올리면, 파는 사람들이 그 글에 줄을 섭니다.

## 2. 왜 만드는가

기존 중고 거래(당근마켓 등)는 **판매자 주도**입니다. 파는 사람이 물건을 올리고, 사는 사람이 그중에서 고릅니다. 여기엔 두 가지 구조적 문제가 있습니다.

1. **구매자는 검색과 기다림에 갇힙니다.** 원하는 물건이 올라올 때까지 키워드 알림을 걸고 계속 확인해야 합니다. 원하는 조건(색상, 사이즈, 상태, 가격대)이 구체적일수록 탐색 비용이 기하급수적으로 커집니다.
2. **판매자는 수요를 모릅니다.** 집에 안 쓰는 물건이 있어도 "이게 팔릴까?"를 알 수 없어 올리지 않습니다. 잠재 매물이 시장에 나오지 않습니다.

감자마켓은 **방향을 뒤집어** 이 둘을 동시에 해결합니다. 구매자는 원하는 조건을 한 번만 명확히 적으면 되고, 판매자는 **이미 사겠다는 사람이 있는** 물건만 꺼내면 됩니다.

> **핵심 가설:** "확실한 수요가 보이면, 서랍 속에 잠자던 물건이 시장에 나온다."
> 이 서비스의 성패는 **구해요 글 대비 제안이 붙는 비율**로 판가름납니다.

## 3. 사용자

역할은 **고정되지 않습니다.** 한 사용자가 어떤 글에서는 구매자, 다른 글에서는 판매자입니다.


| 역할                  | 이 서비스에서 하는 일                      | 성공의 정의                   |
| ------------------- | --------------------------------- | ------------------------ |
| **구매자** (구해요 글 작성자) | 원하는 물건의 조건을 올리고, 들어온 제안 중 하나를 고른다 | 원하는 조건에 맞는 물건을 검색 없이 얻는다 |
| **판매자** (제안자)       | 구해요 글을 둘러보고, 가진 물건으로 제안한다         | 팔릴지 고민 없이 확실한 수요에 판다     |


## 4. 핵심 개념 3개

이 세 단어가 서비스 전체를 지탱합니다. 화면과 코드에서 이 용어를 일관되게 씁니다.


| 개념      | 영문(코드)    | 정의                                     |
| ------- | --------- | -------------------------------------- |
| **구해요** | `request` | 구매자가 올린 "이런 물건을 이 가격대에 구합니다" 글         |
| **제안**  | `offer`   | 판매자가 특정 구해요 글에 붙이는 "제가 이걸 이 가격에 팔겠습니다" |
| **거래**  | `deal`    | 구매자가 제안 하나를 수락해 성사된 1:1 매칭             |


**관계:** 구해요 1개 : 제안 N개 → 그중 **정확히 1개**만 수락되어 거래가 된다.

## 5. 핵심 사용자 흐름

### 5.1 구매자 흐름

```
로그인 → 구해요 글 작성 → (기다림) → 제안 목록 확인 → 제안 1개 수락
       → 판매자와 연락 → 거래 완료 처리
```

1. 구해요 글을 쓴다: 제목, 설명, 카테고리, **희망 가격 범위**, 거래 지역, 사진(선택), 마감일
2. 제안이 들어오면 목록에서 본다: 제안가, 물건 상태, 사진, 판매자 메시지
3. 마음에 드는 제안 하나를 **수락**한다 → 나머지 제안은 자동으로 거절 처리된다
4. 수락 시점에 서로의 연락 수단이 공개된다
5. 실제 거래 후 **거래 완료**를 누른다

### 5.2 판매자 흐름

```
로그인 → 구해요 목록 둘러보기/검색 → 글 하나 선택 → 제안 작성
       → (기다림) → 수락 알림 확인 → 구매자와 연락 → 거래
```

1. 구해요 목록을 최신순/카테고리/지역으로 훑는다
2. 내가 가진 물건과 맞는 글을 찾는다
3. 제안을 쓴다: 제안 가격, 물건 상태, 사진(필수), 한 줄 메시지
4. 수락되면 알림을 받고 연락 수단이 공개된다
5. 수락 전까지는 **제안을 철회**할 수 있다

### 5.3 상태 전이

**구해요(`request`)**

```
open ──(제안 수락)──► matched ──(거래 완료)──► completed
  │
  ├──(작성자가 닫음)──► closed
  └──(마감일 경과)────► expired
```

**제안(`offer`)**

```
pending ──(구매자가 수락)──► accepted
   │
   ├──(다른 제안이 수락됨)──► rejected   (자동)
   └──(판매자가 철회)──────► withdrawn
```

> **불변 조건:** 하나의 구해요 글에 `accepted` 상태의 제안은 **최대 1개**. 이건 애플리케이션 로직이 아니라 **DB 제약으로 강제**해야 합니다(동시 수락 방지).

> **`expired`는 저장되는 값이 아닙니다.** v1에서 `expired`는 `expires_at` 기준의 **파생 상태**입니다. `expires_at <= now()`이고 `status = 'open'`인 글은 조회 시 `expired`로 내려가고 기본 목록에서 빠집니다. 상태를 실제로 갱신하는 만료 배치는 두지 않습니다. (Q2와 함께 검토할 것)

## 6. 기능 요구사항

### F0. 인증 / 프로필

- Supabase Auth 이메일/비밀번호로 가입·로그인·로그아웃한다
- **가입 직후에는 `profiles` 행이 없다.** 최초 로그인 시 닉네임을 입력해야 서비스를 쓸 수 있다
- 닉네임은 유일하다. 중복 저장은 **DB UNIQUE 제약**으로 막는다
- 세션은 브라우저 재방문 후에도 유지된다
- 비로그인 사용자가 보호 화면에 접근하면 로그인 화면으로 보내고, 로그인 후 원래 목적지로 돌려보낸다
- 연락 수단(`contact_type` / `contact_value`) 컬럼은 만들되 **v1 M0에서는 입력받지 않고 어떤 응답에도 담지 않는다**

**수용 조건**

- [ ] 잘못된 비밀번호로 로그인하면 실패 메시지가 뜨고, **계정 존재 여부는 구분해 알리지 않는다**
- [ ] 프로필 없는 로그인 사용자는 어떤 보호 화면에 들어가도 온보딩으로 보내진다
- [ ] 동시에 같은 닉네임을 저장하면 하나만 성공하고 다른 하나는 409를 받는다
- [ ] 어떤 API 응답에도 연락 수단이 포함되지 않는다

### F1 구해요 글 작성 / 관리

- 필수: 제목, 설명, 카테고리, 희망 최저가~최고가, 거래 지역
- 선택: 참고 사진(최대 3장), 마감일(기본 14일 후)
- 작성자는 자기 글을 수정/삭제/조기 마감할 수 있다. **단 제안이 하나라도 달린 글은 삭제할 수 없고 조기 마감만 가능하다** (글이 사라지면 제안자의 제안도 함께 사라지므로)
- **제안이 하나라도 달린 뒤에는 가격 범위와 카테고리를 수정할 수 없다** (제안자의 판단 근거가 바뀌므로)
- **카테고리는 자유 태그다** (Q4 확정). 고정 목록을 두지 않고 텍스트로 입력받으며, 서버는 길이만 검증한다

**수용 조건**

- [ ] 필수 항목이 비면 제출 버튼이 눌리지 않고 어떤 항목이 비었는지 표시된다
- [ ] 최저가 &gt; 최고가면 저장되지 않는다
- [ ] 남의 글을 수정/삭제하려는 요청은 403으로 막힌다
- [ ] 제안이 달린 글에서 가격 범위 입력란은 비활성화되고 이유가 표시된다

### F2. 구해요 목록 / 상세

- 목록: 최신순 기본, 카테고리·지역·상태(구하는 중만 보기) 필터
- 제목·설명 키워드 검색
- 각 항목에 **제안 수**를 표시한다 (판매자가 경쟁 정도를 판단하는 핵심 정보)
- 상세: 글 전문 + 제안 수 + (작성자 본인이면) 제안 목록
- **구현 시점:** 목록의 기본 정렬·페이지네이션·기본 제외 규칙(마감/성사/만료 글 숨김)은 **M1**, 검색과 필터 파라미터는 **M4**에서 구현한다

**수용 조건**

- [ ] 목록이 비어 있으면 "아직 구해요 글이 없어요" 빈 상태 화면이 보인다
- [ ] 마감/성사된 글은 기본 필터에서 제외된다
- [ ] 제안 내용(가격·판매자)은 **글 작성자 본인에게만** 보인다. 타인이 조회하면 개수만 보인다

### F3. 제안

- 제안 시 입력: 제안 가격, 물건 상태(새것/거의 새것/사용감 있음/하자 있음), 사진 **최소 1장**, 메시지
- **한 사용자는 같은 구해요 글에 제안을 1개만** 할 수 있다 (수정은 가능)
- **자기 글에는 제안할 수 없다**
- 수락 전까지 철회 가능

**수용 조건**

- [ ] 사진 없이 제출하면 거부된다
- [ ] 이미 제안한 글에 다시 제안하면 새로 만들어지지 않고 기존 제안이 수정된다
- [ ] 자기 글에 제안하려 하면 버튼이 보이지 않고, API 직접 호출 시 400으로 막힌다
- [ ] 마감/성사된 글에는 제안할 수 없다

### F4. 수락과 거래

- 구매자가 제안 1개를 수락 → 해당 제안 `accepted`, 나머지 전부 `rejected`, 글은 `matched`
- 수락 즉시 양쪽에 서로의 닉네임과 연락 수단이 공개된다
- 거래 완료 처리는 **구매자가** 한다 (아래 열린 질문 Q1 참조)
- 수락은 **되돌릴 수 없다** (MVP). 문제가 생기면 글을 닫고 새로 올린다

**수용 조건**

- [ ] 수락 후 다른 제안의 상태가 모두 `rejected`로 바뀐다
- [ ] 두 요청이 동시에 서로 다른 제안을 수락하려 해도 **하나만 성공**하고 다른 하나는 409를 받는다
- [ ] 수락 전에는 어느 쪽도 상대의 연락 수단을 볼 수 없다
- [ ] 거래 완료 후 글 상태가 `completed`가 되고 더 이상 제안을 받지 않는다

### F5. 내 활동

- 내가 쓴 구해요 글 목록 (상태별)
- 내가 보낸 제안 목록 (상태별)
- 각 항목에서 바로 해당 글로 이동

**수용 조건**

- [ ] 로그인한 사용자만 접근할 수 있다
- [ ] 제안이 수락/거절된 것을 이 화면에서 확인할 수 있다

## 7. 비기능 요구사항

### 7.1 모바일 (최우선)

이 서비스는 **모바일에서 쓰이는 것이 기본**입니다. 데스크톱은 대응은 하되 최적화 대상이 아닙니다.

- **모바일 퍼스트 반응형 웹.** 기준 뷰포트 **375px 폭**부터 깨지지 않아야 한다
- 하단 고정 탭 네비게이션 (홈 / 검색 / 글쓰기 / 내 활동)
- 터치 타겟 **최소 44×44px**, 주요 액션 버튼은 엄지가 닿는 화면 하단에 배치
- 사진 업로드는 **카메라 직접 촬영**을 지원한다 (`capture` 속성)
- 입력 폼은 필드별로 적절한 키보드를 띄운다 (가격 → 숫자 키패드)
- 가로 스크롤이 발생하면 버그로 간주한다

**수용 조건**

- [ ] 375px 폭에서 모든 화면에 가로 스크롤이 없다
- [ ] 모든 버튼/링크의 터치 영역이 44px 이상이다
- [ ] 사진 첨부 시 모바일에서 카메라 선택지가 뜬다

### 7.2 성능

- 목록 첫 화면이 **3G 환경에서 3초 이내** 표시
- 목록은 20개 단위 페이지네이션 (무한 스크롤은 v2)
- 업로드 이미지는 **긴 변 1280px, 80% 품질로 압축**해 저장한다

### 7.3 보안 / 프라이버시

- 연락 수단은 **거래 성사 전까지 어떤 API 응답에도 포함되지 않는다**
- 모든 테이블에 RLS를 적용한다
- 사용자 식별은 검증된 JWT에서만 가져온다 (요청 본문의 user_id를 신뢰하지 않는다)
- 모든 에러 응답은 `{ "code", "message" }` 형태를 가지며, **`code`는 화면 분기에 쓸 수 있는 고정 문자열**이다. 에러 본문에 스택 트레이스·SQL 문·환경변수 값을 넣지 않는다

### 7.4 접근성

- 모든 이미지에 대체 텍스트
- 폼 입력에 연결된 레이블
- 색상만으로 상태를 구분하지 않는다 (상태 배지에 텍스트 병기)

## 8. 데이터 모델 (개략)

정확한 스키마는 백엔드 스펙에서 확정합니다. 여기서는 **개념 모델**만 정의합니다.

```
profiles          사용자 프로필
  id (= auth.users.id), nickname, contact_type, contact_value, created_at
  ── UNIQUE(nickname)                              : 닉네임은 유일
  ── 행은 가입 시 자동 생성되지 않고 온보딩에서 만들어짐

requests          구해요 글
  id, buyer_id → profiles, title, description, category,
  price_min, price_max, region, status, expires_at, created_at

request_images    구해요 참고 사진 (0~3장)
  id, request_id → requests, url, sort_order

offers            제안
  id, request_id → requests, seller_id → profiles,
  price, condition, message, status, created_at
  ── UNIQUE(request_id, seller_id)                 : 1인 1제안
  ── UNIQUE(request_id) WHERE status = 'accepted'  : 수락은 글당 1개

offer_images      제안 사진 (1장 이상)
  id, offer_id → offers, url, sort_order
```

**주의:** 위 두 개의 부분 유니크 인덱스가 이 서비스의 **핵심 무결성 장치**입니다. 애플리케이션 코드의 if 문으로 대체하지 마십시오.

## 9. 범위 밖 (v1에서 하지 않는 것)

명시적으로 하지 않습니다. 요청이 들어와도 v2로 미룹니다.

- **실시간 채팅** — 수락 후 연락 수단 공개로 대체
- **결제 / 에스크로 / 배송** — 직거래만 가정
- **푸시 알림** — 화면 진입 시 확인하는 방식. (이메일 알림은 여력 되면 검토)
- **평점 / 후기 / 신뢰도** — 거래량이 쌓인 뒤에 의미가 생김
- **지도 / GPS 기반 동네 인증** — 지역은 자유 입력 텍스트
- **네이티브 앱 / PWA 설치** — 반응형 웹만
- **경매식 자동 낙찰** — 수락은 사람이 한다
- **신고 / 차단 / 관리자 도구** — 실습 범위 밖

## 12. 열린 질문 (사람이 결정해야 함)

구현 전에 답이 필요합니다. 추측으로 채우지 마십시오.

- **Q1. 거래 완료는 누가 확정하나?**
  - (a) 구매자만 — 단순하지만 구매자가 안 누르면 영원히 `matched`에 남는다
  - (b) 양쪽 모두 눌러야 완료 — 정확하지만 화면과 상태가 늘어난다
  - (c) 어느 한쪽이 누르면 완료 — 분쟁 소지
  - *현재 문서는 (a)로 가정하고 작성됨. 확정 필요.*
- **Q2. 마감일이 지난 글의 제안은 어떻게 되나?** 자동 거절인가, 그대로 두고 글만 `expired`인가?
- **Q3. 연락 수단을 가입 시 필수로 받나?** 필수로 하면 가입 이탈이 늘고, 선택으로 하면 수락 시점에 다시 받아야 한다. — *M3 착수 전까지 필요. M0/M1은 "NULL 허용 + 어떤 응답에도 미노출"로 진행.*
- **Q5. 이미지 저장은 Supabase Storage인가?** 그렇다면 버킷 공개 정책을 어떻게 잡을 것인가. — *M2 착수 전까지 필요(제안 사진은 최소 1장 필수).*

### 확정된 질문

- **~~Q4. 카테고리 목록을 고정할 것인가?~~ → 자유 태그로 확정** (2026-08-13). 텍스트 입력 + 길이 검증만. 고정 목록을 두지 않는다. **대가:** M4에서 필터를 붙일 때 "아이폰"과 "아이폰14"가 다른 카테고리가 되는 문제를 그때 다뤄야 한다(정규화 또는 부분 일치).
- **~~Q6. Supabase Auth의 이메일 확인(Confirm email)을 켤 것인가?~~ → 끄기로 확정** (2026-08-13). 가입 즉시 세션이 생겨 온보딩으로 직행한다. Supabase 프로젝트 설정에서 **명시적으로 꺼야 한다**(기본값이 켜짐). 실습·강의 흐름에서 메일함 왕복을 없애려는 결정이며, 실서비스 전환 시 재검토 대상이다.

## 13. 전제 / 제약

- **DB / 인증: Supabase (Postgres + Auth)**. Supabase 프로젝트 인증 정보는 **아직 없으며 추후 입력**합니다. 그때까지 개발은 로컬 Supabase 또는 목 데이터로 진행하고, 모든 접속 정보는 환경변수로만 참조합니다. **키를 코드에 하드코딩하지 마십시오.**
- 웹은 Vercel에 배포합니다.
- **FastAPI의 배포 대상은 미정입니다.** 로컬 개발은 `http://localhost:8000`을 가정하고, 웹은 API 베이스 URL을 **환경변수로만** 참조합니다. 배포처는 M5 착수 전까지 정하면 됩니다.
- 이 프로젝트는 **강의 실습용**입니다. 기능의 완성도보다 **스펙 주도 개발과 TDD 흐름을 보여주는 것**이 우선입니다. 기능을 늘리기보다 §9의 범위 밖을 지키십시오.
