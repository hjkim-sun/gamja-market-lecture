# 인증과 프로필 (M0)

> 대상 마일스톤: **M0 — 프로젝트 골격 + 인증**
> 근거: PRD §5(핵심 사용자 흐름), §7.3(보안/프라이버시), §8(`profiles`), §11(M0), §13(전제)
> **역반영 완료:** 이 스펙 작성 시점에는 PRD §6에 인증 섹션이 없어 본문의 단서로부터 요구사항을 복원했습니다. **PRD 0.2에 `F0. 인증 / 프로필`로 반영되었습니다.**

## 목적

방문자가 이메일/비밀번호로 감자마켓 계정을 만들고, 로그인 상태를 브라우저 재방문 후에도 유지하며, 거래 상대에게 보일 최소 신원(닉네임)을 등록한다.

## 사용자 시나리오

1. 방문자가 가입 화면에서 이메일과 비밀번호를 입력해 계정을 만든다.
2. 가입 직후에는 프로필이 없으므로 **온보딩 화면**으로 이동해 닉네임을 입력한다.
3. 닉네임을 저장하면 홈(구해요 목록)으로 이동한다.
4. 로그아웃한 뒤 같은 계정으로 다시 로그인하면 온보딩을 거치지 않고 바로 홈으로 간다.
5. 비로그인 상태로 보호된 화면 URL을 직접 열면 로그인 화면으로 보내지고, 로그인에 성공하면 원래 가려던 화면으로 돌아온다.
6. 로그인한 사용자가 브라우저를 새로고침하거나 탭을 다시 열어도 로그인 상태가 유지된다.
7. 이미 쓰이고 있는 닉네임을 입력하면 저장되지 않고 화면에 이유가 표시된다.

## 데이터

### 신규 테이블 `profiles`

| 컬럼 | 타입 | 제약 |
|---|---|---|
| `id` | uuid | PK, `auth.users.id` 참조, `ON DELETE CASCADE` |
| `nickname` | text | NOT NULL, **UNIQUE**, 길이 2~20 |
| `contact_type` | text | NULL 허용 (미결정 Q3) |
| `contact_value` | text | NULL 허용 (미결정 Q3) |
| `created_at` | timestamptz | NOT NULL, 기본값 `now()` |

- **RLS를 켠다.** 본인 행만 select/insert/update 가능한 정책을 함께 둔다.
- **가입 시점에 `profiles` 행을 자동 생성하지 않는다.** 행은 온보딩에서 사용자가 닉네임을 저장할 때 처음 만들어진다. 따라서 "로그인은 되어 있으나 `profiles` 행이 없는 상태"가 정상적으로 존재하며, 모든 보호 화면과 쓰기 API는 이 상태를 다뤄야 한다.
- `contact_type` / `contact_value`는 M0에서 **입력받지 않고, 어떤 API 응답에도 포함하지 않는다.** 컬럼만 만들어 둔다(PRD §7.3: 연락 수단은 거래 성사 전까지 어떤 API 응답에도 포함되지 않는다).

## API 계약

### 역할 분담

- **가입 / 로그인 / 로그아웃 / 세션 갱신은 FastAPI를 거치지 않는다.** 브라우저가 supabase-js(`@supabase/ssr`)로 Supabase Auth와 직접 통신한다.
- **프로필 조회/저장은 FastAPI를 경유한다.** FastAPI는 `Authorization: Bearer <supabase JWT>`를 검증하고, 사용자 식별은 검증된 토큰의 `sub`에서만 가져온다. 요청 본문의 user_id는 신뢰하지 않는다.

### 공통 에러 봉투

모든 에러 응답은 다음 형태를 갖는다. 구체 형태의 최종 확정권은 `backend-developer`에게 있으나, **`code` 필드가 기계 판독 가능한 문자열로 반드시 존재해야 한다.**

```json
{ "code": "nickname_taken", "message": "이미 사용 중인 닉네임입니다." }
```

### `GET /me`

- 요청: 인증 필요.
- 200: `{ "id": "<uuid>", "nickname": "<string>", "created_at": "<iso8601>" }`
- 401 `unauthorized` — 토큰 없음 / 만료 / 서명 검증 실패
- 404 `profile_not_found` — 인증은 되었으나 `profiles` 행이 아직 없음 (= 온보딩 미완료)
- 응답에 `contact_type` / `contact_value`를 **포함하지 않는다.**

### `PUT /me`

프로필 최초 생성과 수정을 겸한다(upsert).

- 요청 본문: `{ "nickname": "<string>" }`
- 200: `GET /me`의 200과 동일한 본문
- 400 `validation_error` — 닉네임이 없음 / 2자 미만 / 20자 초과 / 공백만으로 구성됨
- 401 `unauthorized`
- 409 `nickname_taken` — 다른 사용자가 이미 쓰는 닉네임

## 수용 조건

### 가입

- [ ] AC1: 유효한 이메일과 비밀번호로 가입하면 세션이 생성되고 `/onboarding`으로 이동한다.
- [ ] AC2: 이미 가입된 이메일로 가입을 시도하면 화면에 에러 메시지가 표시되고 `/onboarding`으로 이동하지 않는다.
- [ ] AC3: 이메일 형식이 아닌 값 또는 6자 미만 비밀번호로는 제출 버튼이 동작하지 않고, 어떤 항목이 왜 잘못됐는지 필드 옆에 표시된다.
- [ ] AC4: 비밀번호 입력란의 값은 화면에 마스킹되어 표시된다.

### 온보딩(프로필 최초 입력)

- [ ] AC5: `profiles` 행이 없는 로그인 사용자가 `/`(홈) 또는 임의의 보호 화면을 열면 `/onboarding`으로 이동한다.
- [ ] AC6: 닉네임을 저장하면 `PUT /me`가 200을 반환하고 화면은 `/`로 이동한다. 이후 홈을 다시 열어도 `/onboarding`으로 되돌아가지 않는다.
- [ ] AC7: 1자 또는 21자 닉네임을 제출하면 `PUT /me`가 400 `validation_error`를 반환하고, 화면에 에러 메시지가 남으며 이동하지 않는다.
- [ ] AC8: 다른 사용자가 쓰는 닉네임을 제출하면 409 `nickname_taken`을 받고, "이미 사용 중인 닉네임"임을 알리는 메시지가 화면에 표시된다.
- [ ] AC9: 두 요청이 동시에 같은 닉네임을 저장하려 하면 **하나만 200이고 다른 하나는 409**를 받는다(UNIQUE 제약으로 강제. 애플리케이션의 사전 조회 if 문으로 대체하지 않는다).

### 로그인 / 로그아웃 / 세션

- [ ] AC10: 올바른 이메일/비밀번호로 로그인하면 홈으로 이동하고, 화면 어딘가에 자신의 닉네임이 표시된다.
- [ ] AC11: 잘못된 비밀번호로 로그인하면 화면에 로그인 실패 메시지가 표시되고 홈으로 이동하지 않는다. 메시지는 "이메일이 없는지" / "비밀번호가 틀렸는지"를 구분해 알려주지 않는다(계정 존재 여부 노출 금지).
- [ ] AC12: 로그아웃하면 세션이 제거되고 `/login`으로 이동한다. 이후 뒤로 가기로 보호 화면에 접근해도 `/login`으로 다시 보내진다.
- [ ] AC13: 로그인 상태에서 페이지를 새로고침해도 로그인 상태가 유지된다(세션 쿠키가 미들웨어에서 갱신된다).
- [ ] AC14: 비로그인 상태로 `/requests/new`를 직접 열면 `/login`으로 이동하고, 로그인에 성공하면 `/requests/new`로 돌아온다.
- [ ] AC15: 로그인 상태로 `/login` 또는 `/signup`을 열면 홈으로 이동한다.

### API 인증

- [ ] AC16: `Authorization` 헤더 없이 `GET /me`를 호출하면 401 `unauthorized`를 받는다.
- [ ] AC17: 서명이 유효하지 않거나 만료된 JWT로 `GET /me`를 호출하면 401 `unauthorized`를 받는다.
- [ ] AC18: 사용자 A의 토큰으로 호출한 `GET /me`는 A의 프로필만 반환한다. 요청 본문이나 쿼리 파라미터로 다른 user_id를 전달해도 응답이 바뀌지 않는다.
- [ ] AC19: `GET /me` / `PUT /me`의 어떤 성공 응답에도 `contact_type` / `contact_value`가 포함되지 않는다.
- [ ] AC20: 에러 응답 본문에 스택 트레이스, SQL 문, 환경변수 값이 포함되지 않는다.

### 골격 / 환경

- [ ] AC21: `web/`과 `api/` 각각에서 테스트 러너를 실행하면 최소 1개의 테스트가 통과한다(`web/`: vitest, `api/`: pytest).
- [ ] AC22: `web/.env.example`과 `api/.env.example`이 존재하고, 실제 키 값이 아닌 자리표시자만 담고 있다.
- [ ] AC23: `service_role` 키가 `NEXT_PUBLIC_` 접두사를 가진 어떤 변수에도, `web/` 소스 어디에도 등장하지 않는다.
- [ ] AC24: 375px 폭에서 가입/로그인/온보딩 화면에 가로 스크롤이 없고, 모든 버튼의 터치 영역이 44×44px 이상이다.
- [ ] AC25: 모든 폼 입력에 연결된 레이블이 있어 접근 가능한 이름으로 조회할 수 있다.

## 범위 밖 (Non-goals)

- 소셜 로그인(구글/카카오 등), 매직 링크 로그인
- 비밀번호 재설정 / 이메일 변경 / 회원 탈퇴
- 연락 수단(`contact_type`, `contact_value`) 입력 화면 — 컬럼만 만들고 화면은 만들지 않는다. 실제로 필요한 시점은 수락이 생기는 M3이며, 필수 여부가 아직 미결(Q3)이다.
- 프로필 사진, 자기소개
- 닉네임 변경 이력, 변경 횟수 제한
- 관리자 계정 / 권한 등급

## 미결정 사항

- **Q3(PRD §12). 연락 수단을 가입 시 필수로 받는가?**
  이 스펙은 "M0에서는 받지 않고 컬럼을 NULL 허용으로 둔다"는 **가정** 위에 작성되었다. 이 가정은 M0/M1을 진행 가능하게 하지만, 나중에 "가입 시 필수"로 결정되면 온보딩 폼과 `PUT /me` 계약, `profiles` NOT NULL 제약을 다시 손봐야 한다. **M3 시작 전까지는 반드시 답이 필요하다.**
- **~~Q6. Supabase Auth의 이메일 확인(Confirm email)을 켜는가?~~ → 끄기로 확정** (2026-08-13, PRD §12).
  가입 즉시 세션이 생기므로 AC1이 그대로 성립한다. **단 Supabase 기본값은 "켜짐"이므로 프로젝트 설정에서 명시적으로 꺼야 한다.** 이 설정이 안 꺼져 있으면 AC1·AC5·AC6이 전부 실패하며, 그때의 증상은 "가입은 됐는데 온보딩으로 안 넘어감"이다. **T2 착수 시 이 설정부터 확인할 것.**
- 비밀번호 최소 길이는 Supabase 기본값(6자)을 따른다. 더 강한 정책이 필요하면 알려줄 것.
